# ExecPlan Specification

## Purpose / Big Picture
Describe the high-level goal of your task or feature. Explain why this work is being done and how it fits into the broader project. Provide context for a novice developer or agent so they can understand the "why" before diving into the "what".

## Progress
Track progress here as you implement the plan. Use a checklist to indicate milestones and tasks. Check off items as they are completed. This section should be updated as work proceeds.

## Surprises & Discoveries
Note any unexpected obstacles, new information, or changes that arise while executing the plan. This could include issues discovered, additional requirements, or interesting learnings.

## Decision Log
Document important decisions made during the implementation. For each decision, record the options considered, the rationale behind the choice, and any trade-offs. This helps future readers understand the reasoning and revisit decisions if necessary.

## Outcomes & Retrospective
After the work is completed, summarize the final outcome and reflect on what went well, what didn't, and what could be improved. Include any metrics or acceptance criteria that demonstrate success.

## Context and Orientation
Provide any background details required to execute the plan. This might include repository structure, relevant files, environment setup instructions, or links to designs and APIs. Assume a novice will have no prior context.

## Plan of Work
Outline the overall approach you intend to take. Describe the phases or stages of work and the logical order in which they should be tackled. This should provide a clear roadmap from start to finish.

## Concrete Steps
List the specific actionable steps required to complete the plan. Each step should be clear and executable by an agent or developer. Use checklist items for tasks so progress can be tracked.

## Validation and Acceptance Criteria
Define how the completed work will be tested and validated. Specify the criteria that must be met for the work to be considered complete. Include manual and automated testing steps if relevant.

## Idempotence
Explain how the plan can be executed multiple times without causing unintended side effects. Include cleanup steps, idempotent operations, or safeguards to ensure that running the plan repeatedly does not break the environment.

## Artifacts
List any files, documents, or other artifacts that will be produced as part of this plan. Explain where they should be stored in the repository and how they will be used.

## Interfaces
Describe any interfaces, APIs, or integration points affected by this work. Note what contracts must be maintained and any changes that are introduced.
